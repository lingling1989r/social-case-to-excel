# 变体：把评论区当成「需求洞察」来源

标准流程里评论只用来补数字或用例（`reddit_get_thread` 取评论树）。但用户经常会明确要求：

> 「挖掘下评论区，要把评论区作为**洞察实际需求**和**做二次判断**的来源」

这时评论不再是脚注，而是**与正文平级的洞察列**。本文件记录这条变体的全部动作——跑过一批 B站 + X 混排（46 条案例、抓取 45 条的评论共 1785 条含楼中楼）后的沉淀。

## 1. 什么时候走这条变体

用户提到：评论区洞察 / 评论里的真实需求 / 看评论怎么说 / 有没有人反驳 / 二次判断 / 从评论里找痛点。只要出现这类意图，就走这里；否则按主流程走（评论只用于补数字）。

## 2. 抓取侧的差异

| 平台 | 主楼 | 楼中楼/回复 | 排序 | 每条量级 |
|---|---|---|---|---|
| B站 | 视频评论接口，主楼 | 递归取楼中楼 | 可按热度 | 主楼前 20–40 条 + 楼中楼 |
| X | 帖子回复接口 | 平铺回复 | **无点赞字段，无法按热度排**，只能按返回顺序抽样 | 4–107 条 |
| Reddit | `reddit_get_thread(top_n=N)` | 评论树 | 按热度 | 按 `top_n` |

三条要点：

- **X 回复没有点赞数**，所以「按热度取前 N 条」在这个平台上做不到；口径要如实写成「按接口返回顺序抽样 4–107 条」，不要含蓄地写成「按热度」。
- **B站主楼与楼中楼要分开记数**：只看主楼会漏掉最长的争论串（本批多条洞察来自楼中楼里的反驳）。
- **落盘建议**：`comments.json` 形如 `{tid: <任意嵌套>}`。下游一律**递归取字符串**（dict/list 都走一遍，只要 `isinstance(x, str) and len(x) > 1`），不要假设固定层级——两个平台的嵌套深度不一样。

抓取完成后，在「口径与说明」里写清三件事：抓了多少条案例的评论、合计多少条、以及各平台的取数口径。模板见第 5 节。

## 3. 交付形态的差异（两处新增）

1. **总表新增第 25 列「评论区洞察（真实需求 + 二次判断）」**，并且**追加在末尾**——不要插在中间，按列号取值的 QA 会读错列而且不报错（同 `pipeline.md` 6.0.2 的「总表加一列平台」）。
2. **新增 `7-评论区洞察` sheet**，逐条陈列而不是把长文塞在总表里。列：`案例编号 / 优先级 / 所属线 / 平台 / 案例主体(简) / 评论总数(平台口径) / 本轮抓取条数 / 评论区洞察 / 来源账号`。

写作要求（这是这条变体的价值所在，不能糊弄）：

- **写归纳出的结论，不写评论摘抄**。④ 条编号式结论比堆原话有用得多，代表性原话只挑 1–2 句放进总表的长单元格里。
- **把「真实需求」和「二次判断」分清楚**：前者是评论者在问什么/要什么（愿意付 20 美金取英文名、手工编一个结要 6 小时），后者是评论者对正文结论的反驳或修正（「门槛低到人人能做时，平台凭什么把流量分给新人」）。这类反驳往往比正文更值钱，**不要因为与正文结论相左就删掉**。
- **标注证据性质**：评论是**个体自述口径**，与正文一起引用时在「证据强度/风险」列写明；B站评论区还有大量**引流与卖课**内容（「本期视频的引流法已帮 11 位同学出单」这类），作为需求信号可以引用，但必须标明是带货动机。

## 4. QA 侧的两个契约（不遵守，闸门会给出误导性红灯）

### 4.1 核对池必须并入评论原文 + 平台指标 + 账号名

`qa_09` 是「中文里的数字是否能在原帖池里找到」的反查。**洞察列里引用的评论数字天然不在原帖正文里**，如果核对池（`<tag>_sel_qa.json`）只放原帖正文，一批会报出几十条假可疑（本批首次跑 94 项）。

补池内容（写个小 patch 脚本追加到每条 `text` 末尾即可，不必改 QA 脚本）：

```
来源账号：<screen_name>
平台指标（抓取当日快照）：播放/浏览 X，点赞/收藏 Y，评论 Z，转发 W
评论区原文（含楼中楼，本条与本批写作直接引用）：<comments.json 递归取出的全部字符串>
```

两个副产物值得注意：

- **平台指标行**顺手解决了另一个老问题：写作列里一旦出现「播放 52 万、收藏 1.17 万」这类平台互动量，原先只能靠「不写」来规避（见 SKILL.md 第 16 条）。有指标行在池里之后，互动量可以照写，但**四舍五入必须 ≤1%**（本批 6 处超标：`3.5 万`→`3.54 万`、`1.1 万`→`1.15 万`、`3.1 万`→`3.14 万`）。容差是 1%，不是「看着差不多」。
- **账号名**入池后，`@handle` 里的数字（`bili_26029121`、`moon203954`）仍属已知假报，不必再逐条解释。

### 4.2 数字缩写归一化（一次把口语写法清干净）

中文社媒大量使用 `900w` / `10w` / `3.3w` / `1万1` / `底薪 5-7k` 这类写法，而 QA 的单位表不认识 `w`，也读不出「1万1」。做法是**在池尾追加一个等价展开块**（不改任何写作数据、不改脚本）：

```
数字缩写归一化（与原帖等价，供机器核对）：900w = 9000000；1万1 = 11000；5-7k = 5000 到 7000
```

三个必须踩准的细节（都是实测踩过的）：

1. **`1万1` = 1×10000 + 1×**1000** = 11000**，不是 10001。中文口语的尾数位默认是「千」位。写成 `X*10000 + Y*1000`。
2. **展开值必须用 `%d` 整数格式化，绝不能用 `%g`**。`%g` 会把 900 万输出成 `9e+06`，而数字正则从 `9e+06` 里只解析出 `9`——于是 900 万这个数字**等于没加进去**，报错信息还是一模一样的「原帖找不到 9000000」。
3. **patch 必须幂等**。它是在既有 `text` 上追加内容，重复运行会把旧块和新块叠在一起（旧块用的是旧公式/旧格式化），于是**前一次的错误写法继续生效**，看着像「改了没用」。做法：追加前先用正则把 `\n*数字缩写归一化（与原帖等价，供机器核对）：[\s\S]*$` 从原文里剥掉。

匹配正则（够用，别过度设计）：

```python
r'(\d+(?:\.\d+)?)\s*[wW](?![A-Za-z0-9])'              # 900w / 3.3w
r'(\d)\s*万\s*(\d)(?!\d)'                              # 1万1（尾数按千位）
r'(\d+(?:\.\d+)?)\s*[-~到至]\s*(\d+(?:\.\d+)?)\s*[kK](?![A-Za-z])'  # 5-7k
```

## 5. 「口径与说明」的两条标准文案

跑完直接把这两条抄进 sheet3（数字填本批实际值），下次就不用再想措辞：

**评论区采集口径**

> 本轮共抓取 N 条案例的评论、合计 M 条（含楼中楼与回复），其余为接口未返回内容的孤例。B站按热度取主楼前 20 到 40 条并合入楼中楼；X 按接口返回顺序抽样 4 到 107 条（X 回复无点赞字段，无法按热度排序）。「评论区洞察」列是把这些评论归纳后的结论，不是评论原文的堆砌。

**数字核对口径**（必须有，否则下次会有人去「修」那两千多个幻影缺失）

> 上线前跑了两向核对：反向（写作里的每个数字是否都能在原帖或评论里找到来源）结果为可疑数字 0 个；正向（原帖数字是否都写进案例）不作为验收指标，因为本轮把 M 条评论原文一并纳入核对池，其中大量数字是日期、序号、楼层、游戏名等与结论无关的内容，案例只保留与结论直接相关的数字。中文口语缩写（900w、1万1、底薪 5-7k）在核对池中已按等价数值展开，不改变写作数据。

**为什么正向这次不作数**：`qa_02` 是字面字符串版的覆盖检查，池里一旦有几千行评论，它报出的缺项数会从「十几项」跳到「两千多项」（本批 2393 项 / 涉及全部 46 条）。这不是数据崩了，是**指标口径不适用**——评论是语料不是待覆盖的事实源。判据始终是**反向 0 条**。这一点要写进 sheet3，不要靠口头解释。

## 6. 已知噪音（引用前先过一眼）

- B站：营销号批量刷屏、评论区高频出现「本期视频的方法已帮 N 位同学出单 / 我已收入 X 美金」这类**引流话术**——需求信号可引，商业动机必须标。
- X：评论区有卖课、灰产、假号粉丝报价产业链的内容；作为「真实需求」的反面样本可以引（本批就引了「80 万粉丝的账号报价」这条来佐证假号产业链的规模），但要写清是**自述/黑产口径**，不可当作行业均值。
- 两个平台的数字都是**抓取当日快照**，写进交付说明。
