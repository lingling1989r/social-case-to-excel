# Excel 各 sheet 列定义与内容口径

六 sheet：`1-案例总表` / `2-方法拆解汇总` / `3-口径与说明` / `4-原帖配图` / `5-候选池原始数据` / `6-主题与检索口径`。

---

## sheet 1：案例总表（23 列）

行 = 一条案例，按优先级 `S/A/B/C` 再按所属线排序；`S` 行加底色 `FDE7D3`，`A` 行 `EAF6EC`，`B`/`C` 浅灰。

| # | 列名 | 内容口径 |
|---|---|---|
| 1 | 编号 | 全局序号，1 起；后续所有 sheet 与飞书文档引用它 |
| 2 | 优先级 | `S`（强证据+强可迁移）/ `A` / `B` / `C` |
| 3 | 所属线 | 主题（六线之一） |
| 4 | 案例类型 | `案例` / `案例拆解` / `方法论` —— 方法论帖不声称结果，必须与案例区分 |
| 5 | 案例主体（谁 + 做了什么） | 账号/主体 + 关键动作，一句话 |
| 6 | 起点 → 结果（关键数字） | 保留原帖口径的原始数字（不要换算、不要四舍五入） |
| 7 | 方法拆解（可复制步骤） | ①②③ 编号，每步一个动作，可直接当 checklist |
| 8 | 可迁移到我们 | 对读者自身业务的可用点（面向交付方视角写） |
| 9 | 证据强度 / 风险 | 自述无审计 / 新账号 / 三手转述 / 带 DFY 或私信导流 / 数字内部不自洽等 |
| 10 | 原帖账号 | Reddit 写 `u/name`（`08_build_xlsx.py` 的 `ACC()` 按平台加前缀；X 用 `@handle`） |
| 11 | 原帖链接 | 超链接 |
| 12 | 推文ID | post id，配图与翻译的对齐主键 |
| 13 | 发布时间(UTC) | 原帖时间 |
| 14 | 语种 | 原帖语言 |
| 15–18 | 点赞 / 转发 / 评论 / 浏览 | 抓取当日快照（会变，口径里注明"快照"）；**Reddit 只有点赞与评论两个数，转发/浏览填「—」不填 0** |
| 19 | 原帖配图 | 图片张数，或「无」 |
| 20 | 配图缩略图 | 内嵌图片（`OneCellAnchor`），行高 ~150pt |
| 21 | 正文原文 | 原帖全文，不删减、不改写 |
| 22 | 正文翻译(中文) | 逐段人工译；中文原帖填 `（原帖即中文，免译）` + 原帖全文（**不要留空**，见下） |
| 23 | 案例研究推文（Markdown） | 3 个标题候选 + 故事 + 方法拆解 + 一句话结论 |

> **中文原帖的译文列不能留空。** 填 `（原帖即中文，免译）\n\n` + 原帖全文：留空会让下游 QA 把这条帖的数字全报成「缺失」，前缀也是 `qa_07` 识别中文帖的依据。前缀逐字用这 10 个字（加两个换行共 12 字符），换个写法不会报错、只会让 qa_07 报「中文帖 0 条」。`08_build_xlsx.py` 有内置兜底（CJK 占比 > 15% 自动补），手写时仍建议显式写。批量补的时候写幂等脚本（用标记串判重），别重复追加。
>
> **列名是 QA 的对齐契约。** 加列可以（例如再加一列「原帖发布时间(本地)」），但要保留 `编号` / `优先级` / `所属线` / `正文原文` / `正文翻译` / `案例研究推文` / `推文ID` 这些子串，并在加列后重跑 QA——按列号取值的脚本会读错列而且不报错。若要改第 12 列的表头，新表头里必须仍含 `推文ID`（`qa_09` 靠它对齐行）。

## sheet 2：方法拆解汇总

两段结构，中间空两行分隔：

1. **按线提炼**（列：所属线 / 这一线的共性方法（提炼））—— 每条线一段结论，可直接当方法论目录。
2. **逐条拆解**（列：所属线 / 案例编号 / 案例主体（简）/ 方法步骤（逐条）/ 来源账号）—— 每条案例的步骤拆成一行一条，供逐项打勾。

## sheet 3：口径与说明

收录口径、字段定义、主题说明、免责声明（数字为原帖自述、未审计；配图版权属原帖，仅内部研究使用）。

## sheet 4：原帖配图

列：案例编号 / 优先级 / 所属线 / 案例主体（简）/ 序 / 缩略图 / 类型 / 原图链接 / 来源账号。
缩略图内嵌，原图链接为超链接，便于看高清。

**0 图模式**：取图通道不可用时（media 写成空集 `{}`），这一 sheet 只剩表头、总表的两个配图列留空——这是**允许的交付形态**，但必须在 sheet 3 的配图条目里如实写明「本批未抓取配图（取图通道当期不可用）」，别让客户以为图丢了。措辞用"取图通道不可用"而不是"这批帖子没图"：图床 000 只是网络层事实，判定 0 图之前必须在原始池里数一遍图床域名（pipeline.md 第 4 步有四步判断顺序）。回补后重建，只复跑 `qa_07` 与 `qa_09` 两关。

## sheet 5：候选池原始数据

列：序 / 推文ID / 账号 / 发布时间 / 语种 / 点赞 / 转发 / 评论 / 浏览 / 命中主题 / 命中领域词 / 数字个数 / 正文（截断 400 字）/ 原帖链接。

**保留未入选的候选池**是为了可追溯：客户问「为什么这条没进」时有据可查，也让下一轮挖库可以增量复用。

## sheet 6：主题与检索口径

列：所属线 / 入选案例数 / S / A / B / 该线案例（编号 · 主体简）。
配上每条的检索式，回答「数据怎么来的」。

## 第 23 列：案例研究推文（Markdown）模板

这一列是能直接发出去的成稿，用 `## ` 做故事型标题、`### ` 做四个固定小节。**小节标题必须
逐字使用下面这五个字符串**（`### 标题候选` / `### 故事` / `### 方法拆解` / `### 可直接抄的动作`
/ `### 一句话结论`）——`qa_06_markdown_sections.py` 就是数这五个字符串的出现次数，计数
必须等于案例数。写成 `**标题候选**` 或改用 `## ` 层级不会报错，只会让闸门显示 0，然后你在
交付前才发现要重排 39 条（这一步返工过一次）。

```markdown
## <故事型标题：一句能被复述的判断，不写"案例拆解"这种空话>

### 标题候选
1. <数字冲击角度>
2. <反差角度（别人以为 A，其实是 B）>
3. <方法承诺角度>

### 故事
<3–6 句：谁、起点、干了什么、结果数字。数字与总表第 6 列口径一致，不新增未经原帖支持的数字。>

### 方法拆解
1. <一条一个动作，与原帖步骤对齐>
2. ...

### 可直接抄的动作
- <今天就能执行，带判断门槛（例如"品牌词占比超过 60% 就要警惕"）>
- ...

### 一句话结论
<把这条案例的机制压成一句判断，不是复述数字。>
```

小节之外的自由：标题候选的条数固定 3 条，其余段落长度按原帖信息量走。

## sheet 3：口径与说明 填写模板

sheet 3 是**每条跑批都要重写**的部分（上一轮的主题、轮次数、条数全部不适用）。按下面的
槽位逐条填，槽位后面括号里是这次跑批该填的东西：

| 项 | 填什么 |
|---|---|
| 这份是什么 | 数据源 + 主题 + 分几条线 + 入选条数（标明"不是热点资讯"的筛选意图） |
| 数据来源 | 只写平台 + 「通过平台公开数据接口采集」+ 指标是否为接口返回原值；**不写上游供应商名、端点名、域名**（跑 `qa_11_no_vendor_leak.py` 确认） |
| 时间窗口 | 近 N 天（按抓取日倒推；接口只支持相对天数，写清"截至 <日期> 的近 730/1095 天"） |
| 检索式 | 轮次数 + 组数 + 覆盖的方向清单 + 原始命中唯一帖数 + 过滤后候选池条数（指向 sheet 5） |
| 案例入选标准 | 三条可判定的条件（相关性 / 可量化结果 / 可拆步骤） |
| 排除规则 | 实测剔除的类别（纯资讯、无数字观点帖、无关赛道、article 类型等） |
| 排序口径 | 先归线、线内按优先级、同优先级按点赞降序 |
| 优先级 | S/A/B 各多少条（**用构建脚本按 `data` 现算，别手写**） |
| 案例类型 | 本次实际出现的类型枚举 |
| 方法拆解 | 说明第 7/8 列是重写而非翻译 |
| 正文翻译(中文) | 翻译口径 + 超长帖的处理方式 + 中文原帖不译 |
| 原帖配图 | 有图条数 / 总张数与无图原因（**现算**） |
| 案例研究推文 | 第 23 列的结构 + 独立 markdown 文件名 |
| 行高与长文阅读 | 超上限行数 + 由哪一列驱动（**用 `qa_10_rowheight_overflow.py` 的数字填**，见下） |
| 证据强度/风险 | 自述未审计 + 带商业动机的标注方式 + 二次核实建议 |
| 研究视角 | 第三方整理、不代表原作者观点 |
| 生成时间 | 当日日期 + 星期 |

**行高那条不要靠数**：以 408pt 为上限时，几乎每批都会有 20–30 行被裁切，而"哪一列驱动的"
决定了读者该去开 markdown 还是直接看总表。跑 `qa_10_rowheight_overflow.py` 会直接打印
「N 行超上限 / 最长需要多少 / 驱动列是哪一列」，把那三个数字抄进这条说明即可。

## 内容口径铁律

1. **数字照抄原帖**，不做单位换算与四舍五入；格式差异（`102 万` / `1,025,117`）在 QA 里放过，但不要主动改数。
2. **原文不删减**，翻译不省略；译文缺失比译文略生硬严重得多。
3. **风险字段不留空**——宁可写「无法验证」，也不要让读者以为数字可信。
4. **方法论帖与结果帖分开标注**（`案例类型` 列），别把「我准备这么做」写成「我这么做成了」。
5. 引用原帖观点时标注「原帖自述」；第三方视角的正文里不出现「你可以抄」这类第二人称教程句。
